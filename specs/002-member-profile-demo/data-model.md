# Proposed Data Model: Member Profile Demo

This is a Phase 1 logical/relational design, not a migration or an accepted
production schema. [Spec](spec.md), [plan](plan.md) and
[API contract](contracts/api-v1.md) are the requirements, gates and interface
references. Only synthetic member data is permitted.

## Conventions and classifications

- Internal IDs are server-generated opaque UUIDs, not member/membership numbers.
  SQL primary keys, foreign keys and unique constraints are authoritative.
- `date` values represent calendar dates; audit/decision timestamps are UTC
  instants generated by the server, not trusted client timestamps.
- Mutable domain records have a SQL `rowversion`. Expose only an opaque ETag
  encoding, not an editable property. Updates compare the supplied version in
  the SQL write, not merely in a prior read.
- All strings are Unicode. Required input must be present, non-null and
  nonblank; dates must parse as dates. Contact email must be syntactically valid.
  Mailing address is a required plain-text address in this demo, not an invented
  country-specific postal schema. No age cutoff, phone-country rule, contact
  email uniqueness, future-date prohibition or production eligibility rule is
  inferred. Exact storage lengths and transport bounds require contract/schema
  review before implementation; do not silently truncate or expose values in errors.
- Profile/enrollment fields and request descriptions are sensitive even when
  synthetic. Authentication references and audit actors are restricted,
  privacy-sensitive pseudonymous data. Do not copy any of them to telemetry,
  fixtures containing real people, or AI prompts. Operational telemetry has only
  allowlisted nonpersonal operation/result/duration/correlation metadata.

## Relationships

```text
MemberIdentity 1 ---- 0..1 Enrollment
MemberIdentity 1 ---- 0..1 VerifiedProfileLink ---- 1 MemberProfile
MemberProfile 1 ---- 0..* Membership
Membership 1 ---- 0..* MembershipChangeRequest
MemberIdentity 1 ---- 0..* MembershipChangeRequest (requester)
AuditActor 1 ---- 0..* AuditEvent
```

One current enrollment per identity and one verified link per identity/profile
are the proposed minimal demo representation, not a production re-enrollment
or account-merge policy. Staff-created profiles may have no verified link.
No shared email/name implies a relationship.

## MemberIdentity and AuditActor

<!-- prettier-ignore -->
| Record / field | Type / invariant | Purpose |
| --- | --- | --- |
| MemberIdentity.IdentityId | UUID PK | Internal account reference; never caller-selected. |
| MemberIdentity.Issuer, Subject | Restricted strings; unique pair | Trusted token identity; immutable after creation. Issuer is canonical configured exact issuer, not arbitrary request input. |
| MemberIdentity.AuditActorId | UUID FK, unique | Stable opaque audit reference, not email or token subject. |
| MemberIdentity.CreatedAt | UTC instant | Internal creation time. |
| AuditActor.ActorId | UUID PK | Opaque who-reference for member, staff, or necessary service operation. |
| AuditActor.TrustKind | Member / Workforce / Service | Source trust boundary; not an entitlement. |
| AuditActor restricted identity mapping | Configured issuer + immutable subject or service identity; unique within trust | Supports authorized audit investigation without values in events. |

Member sign-in email belongs to the identity provider. The application does not
need to duplicate it in profile storage; it never uses contact email to resolve
identity. Staff identities do not gain member links automatically. A workforce
audit mapping does not grant staff access: designated workforce entitlement is
checked on each request. No token, OTP, password or client secret is stored.
Create a missing actor mapping within the audited transaction; if required
mapping/audit persistence fails, fail the business mutation.

## Enrollment

<!-- prettier-ignore -->
| Field | Type / invariant |
| --- | --- |
| EnrollmentId | UUID PK |
| IdentityId | FK MemberIdentity, unique |
| Name, ContactEmail, Phone, MailingAddress | Required Unicode strings |
| DateOfBirth | Required date |
| State | `Pending` or `Verified` |
| VerifiedProfileId | Nullable FK MemberProfile; required exactly when Verified |
| VerifiedByActorId, VerifiedAt | Nullable restricted FK/UTC; required exactly when Verified |
| VerificationKind | Null when Pending; `SimulatedExisting` or `SimulatedNew` when Verified |
| CreatedAt, Version | UTC instant, rowversion |

The five required member-submitted fields are stored as a submission snapshot.
No pending enrollment edit or resubmission workflow is required by the spec;
duplicate creation returns a safe conflict instead of replacing it.
Only the submitter or entitled staff can read it. Verification retains the
snapshot; it does not make it public or auto-copy over an existing profile.
FR-003–FR-005 govern the boundary.

## MemberProfile and VerifiedProfileLink

<!-- prettier-ignore -->
| Record / field | Type / invariant |
| --- | --- |
| MemberProfile.ProfileId | UUID PK |
| MemberProfile.MemberNumber | Application-generated immutable nonblank string, unique |
| MemberProfile.Name, ContactEmail, Phone, MailingAddress | Required Unicode strings |
| MemberProfile.DateOfBirth | Required date |
| MemberProfile.CreatedAt, Version | UTC instant, rowversion |
| VerifiedProfileLink.IdentityId | PK/FK MemberIdentity |
| VerifiedProfileLink.ProfileId | FK MemberProfile, unique |
| VerifiedProfileLink.EnrollmentId | FK Enrollment, unique |
| VerifiedProfileLink.VerifiedByActorId, VerifiedAt | Restricted actor FK, UTC instant |

Verification creates the link and changes the enrollment in one transaction.
Its enrollment identity/profile must match the link; enforce via relational
constraints where practical and invariant checks inside the same transaction.
A competing identity cannot claim an already-linked profile. An identity cannot
gain multiple profiles by racing verification. A database uniqueness conflict
rolls back the entire verification operation, including new-profile creation.

Member self-service updates only contact email, phone and mailing address.
Staff update all five profile fields. Neither path changes identity, sign-in
email, member number or verified links. Staff profile creation generates its
number inside the creation workflow. Proposed numbers use an opaque
application-generated category-prefixed random representation, enforced by the
unique index; collision handling must not commit duplicates or unaudited state.
The exact representation is a design-review item, not production numbering policy.

Staff search is restricted to member number, membership number, name or contact
email. Index unique numbers; use reviewed normalized searchable forms/indexes
for names/emails without making them unique or authenticators. Search cannot
bypass staff authorization or leak through request logs. No deletion/inactive
profile workflow is invented.

## Membership

<!-- prettier-ignore -->
| Field | Type / invariant |
| --- | --- |
| MembershipId | UUID PK |
| ProfileId | Required FK MemberProfile; immutable ownership |
| MembershipNumber | Application-generated immutable nonblank string, unique among memberships |
| Type | Exactly `Demo type A` or `Demo type B` |
| Status | Exactly `Demo active` or `Demo ended` |
| StartDate | Required date |
| EndDate | Nullable date; SQL check EndDate is null or EndDate >= StartDate |
| CreatedAt, Version | UTC instant, rowversion |

Numbers are unique in their category, not necessarily across profile and
membership tables. A profile has multiple memberships. Ended memberships are
retained and returned with their original identifier and dates; they are not
deleted or hidden by a default active-only filter.

No inferred rule requires an end date for `Demo ended`, auto-ends by date,
auto-generates an end date, or forbids changing placeholder statuses.
These are demo labels, not production policy. Staff may explicitly maintain
allowed membership fields; members cannot directly update any membership field.

## MembershipChangeRequest

<!-- prettier-ignore -->
| Field | Type / invariant |
| --- | --- |
| RequestId | UUID PK |
| RequesterIdentityId | Required FK MemberIdentity, derived from authenticated caller |
| ProfileId, MembershipId | Required matching ownership; enforce composite relationship to Membership |
| DesiredChange | Required plain text description; sensitive; never an executable command |
| State | `Submitted`, `Approved`, `Rejected`, `Applied` |
| HandoffIsSimulated | Constant true |
| SimulatedHandoffOutcome | `Succeeded` or `Failed`; never means externally approved |
| HandoffFailureCode | Nullable allowlisted nonpersonal code, not exception/provider text |
| SubmittedAt | UTC instant |
| DecisionByActorId, DecisionAt | Null until decision, restricted actor FK and UTC time after decision |
| ApprovedChange | Null unless approved/applied; explicit subset of Type/Status/StartDate/EndDate and presence markers |
| ApprovedMembershipVersion | Null unless approved/applied; membership version reviewed by staff |
| AppliedByActorId, AppliedAt | Null except Applied; restricted actor FK and UTC time |
| Version | rowversion |

The request captures membership/profile/requester association on submit. Server
resolves current verified ownership for every member read; stored requester
alone does not override it. No member chooses an actor or outcome. The internal
handoff simulator returns a labeled success/failure without calling an external
review service, queue or worker. A failed simulation can be persisted visibly
with a Submitted request and audit; the API must not imply a completed review.
Include a minimal failed-handoff outcome event alongside the successful
request-creation event in that transaction; do not copy exception text or prose.

`ApprovedChange` is a language-neutral structured staff allowlist. It must contain
at least one proposed membership field, use valid demo labels/dates, and pass
whole-result membership validation. Explicit null clears EndDate; omission means
unchanged. No ID/number/owner may be included. Store the exact reviewed field
set/values and membership version; application does not accept a replacement
payload. Do not put these values in audit or telemetry.

<!-- prettier-ignore -->
| Transition | Authorized actor and prerequisites | Atomic result |
| --- | --- | --- |
| New -> Submitted | Verified owning member; nonblank desired change | Request plus labeled simulated handoff outcome plus audit. Membership unchanged. |
| Submitted -> Approved | Entitled staff; current request ETag; current membership version and valid structured change | Frozen approved change, decision metadata and audit. Membership unchanged. |
| Submitted -> Rejected | Entitled staff; current request ETag | Recorded rejected outcome and audit. Membership unchanged. |
| Approved -> Applied | Entitled staff; current request ETag; membership still at approved version; change still valid | Membership update, Applied metadata/state and audit together. |
| Any failed decision/application | No legal transition succeeds | Original domain state retained; separate failure audit when available. |

Rejected and Applied are terminal for this demo. Submitted/Rejected cannot be
applied; repeated/concurrent apply never reapplies. A stale membership version
leaves the request Approved and reports conflict. The approved payload cannot
be edited in place; a newly reviewed request is the simplest proposed recovery
when the earlier approved change is no longer applicable. No automatic retry,
implicit external approval or unreviewed application is allowed.

Staff's independent FR-009 membership-maintenance operation remains distinct:
it cannot mark a request Applied, claim to implement a rejected request, or
avoid authorization/audit. A concurrent direct edit invalidates the previously
approved membership version rather than being overwritten.

## AuditEvent

<!-- prettier-ignore -->
| Field | Type / invariant |
| --- | --- |
| EventId | Server-generated UUID PK |
| ActorId | Restricted opaque FK AuditActor; no email, name, subject or token |
| Operation | Allowlisted operation name, including compound verify/apply semantics |
| ChangedFieldNames | Allowlisted field-name set; no before/after values |
| OccurredAt | Server UTC instant |
| Outcome | `Succeeded` or `Failed` |
| FailureCode | Optional allowlisted nonpersonal failure category |
| CorrelationId | Server-controlled nonpersonal operation reference |

Internal events are append-only for the application; access to events and actor
mapping is restricted. No member-facing audit route. Do not store descriptions,
search terms, raw identifiers from rejected paths, request/response payloads,
stack traces, tokens, codes or profile values in audit. One event may describe
the constituent field names of a compound transaction without storing values.

### Write and failure boundaries

1. Authenticate and authorize; resolve a restricted actor from trusted identity.
2. Validate allowlist DTO and owned nested resources, then start the SQL unit of
   work with the required concurrency/version checks.
3. Perform the domain mutation(s) and insert required successful audit event(s)
   using the same connection/transaction. Commit them together.
4. On audit failure or any transaction failure, roll back every domain change.
   Never return a successful unaudited mutation.
5. For authenticated failed attempts, use a separate failure-audit transaction
   when available; rollback of the business transaction must not erase the only
   failure record. A failed audit cannot be made durable while SQL is unavailable;
   report a safe failure and do not claim it was recorded.
6. If commit acknowledgment is lost, the caller must read current state before
   retry. No generic mutation replay loop. Request application checks terminal
   state/version in SQL so a retry cannot reapply an already committed change.

## SQL-backed validation obligations

- Race two verified links against one profile and two profiles against one
  identity; exactly one valid association wins without orphaned new profiles.
- Force duplicate member/membership numbers; unique constraints reject them.
- Enforce membership end/start comparison and retained ended-history reads.
- Roll back enrollment verification and request application at each write/audit/
  commit failure boundary; preserve Approved state on failed apply.
- Race staff maintenance against application and two application attempts;
  prevent stale overwrites/double application.
- Inspect audit content and restricted mapping access using nonpersonal synthetic
  test identifiers. Prove no profile values or request prose leak into audit.

These are future test obligations, not executed results. Private SQL connectivity,
approved US residency, encryption/key decisions, managed-identity permissions and
production retention/deletion policy require the reviews in [plan](plan.md).
